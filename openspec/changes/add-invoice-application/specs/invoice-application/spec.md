## Purpose

让已充值用户可以自助发起开票申请：系统列出本人名下符合条件的人民币余额充值记录，用户勾选若干笔（实付金额合计不低于 300 元）并填写中国增值税发票常见的抬头与接收信息后提交；管理员在后台查看申请内容、审核通过或驳回，并登记实际开具的发票信息。同一笔充值记录至多被一条未释放的申请占用，以避免重复开票。

## ADDED Requirements

### Requirement: 系统列出用户可申请开票的充值记录

系统 SHALL 为登录用户提供可开票充值记录列表。记录 MUST 同时满足：属于当前用户；订单类型为余额充值（`order_type='balance'`）；订单状态为已支付（`PAID`）；支付币种为人民币（`CNY`）；且该订单未被任何未释放的开票申请占用。列表 MUST 以分页形式返回，并包含订单 ID、订单号、支付时间、实付金额、币种与充值赠送金额。

#### Scenario: 列出符合条件的充值记录
- **WHEN** 用户 A 存在两笔已支付的 CNY 余额充值订单，且均未被占用
- **THEN** 系统 MUST 返回这两条记录
- **AND** MUST NOT 返回用户 A 的订阅订单、未支付订单或非 CNY 订单

#### Scenario: 已被申请的充值记录不再出现
- **WHEN** 某笔充值记录已被用户 A 的一条 `PENDING` 申请占用
- **THEN** 该记录 MUST NOT 出现在用户 A 的可开票列表中
- **AND** 该记录 MUST 出现在该申请的状态为 `PENDING` 或 `APPROVED` 时仍被占用，只有驳回或取消后才重新出现

#### Scenario: 非人民币订单不可开票
- **WHEN** 用户持有一笔以 USD 结算的已支付充值订单
- **THEN** 该订单 MUST NOT 出现在可开票列表中

### Requirement: 开票申请金额合计必须达到下限

用户提交开票申请时，系统 MUST 校验所选充值记录的实付金额（`pay_amount`）合计。合计 MUST 大于等于开票金额下限（默认 300 元），否则 MUST 拒绝创建。该下限 MUST 为可覆盖的常量，默认值为 300。

#### Scenario: 合计达到下限
- **WHEN** 用户勾选的充值记录实付金额合计为 300 元
- **THEN** 系统 MUST 接受该申请

#### Scenario: 合计不足下限
- **WHEN** 用户勾选的充值记录实付金额合计为 299.99 元
- **THEN** 系统 MUST 拒绝创建申请并返回可识别的错误码
- **AND** MUST NOT 创建任何申请记录或占用任何充值记录

#### Scenario: 未选择任何记录
- **WHEN** 用户提交开票申请但未选择任何充值记录
- **THEN** 系统 MUST 拒绝创建申请

### Requirement: 一笔充值记录至多被一条开票申请占用

系统 MUST 在数据库层保证同一充值订单 ID 至多被一条未释放的开票申请占用。占用关系 MUST 记录在申请明细上，并 MUST 通过部分唯一索引（`WHERE released_at IS NULL`）实现，使并发提交也无法让同一笔充值被两笔申请同时占用。

#### Scenario: 重复的记录 ID
- **WHEN** 用户提交的充值记录 ID 列表中存在重复 ID
- **THEN** 系统 MUST 对其去重后按去重结果校验

#### Scenario: 提交已被占用的记录
- **WHEN** 用户提交的充值记录中有一笔已被同一用户或另一用户的未释放申请占用
- **THEN** 系统 MUST 拒绝创建申请并指明该记录不可用
- **AND** MUST NOT 占用任何记录

#### Scenario: 并发提交同一笔记录
- **WHEN** 同一用户对同一笔充值记录并发提交两条开票申请
- **THEN** 系统 MUST 至多创建一条申请
- **AND** 另一条 MUST 因唯一约束失败而被拒绝

#### Scenario: 驳回释放占用
- **WHEN** 管理员驳回一条申请
- **THEN** 该申请占用的充值记录 MUST 被释放，重新出现在原用户的可开票列表中
- **AND** 该申请及其明细 MUST 保留以供审计

#### Scenario: 用户取消释放占用
- **WHEN** 用户取消一条待审核申请
- **THEN** 该申请占用的充值记录 MUST 被释放，重新出现在可开票列表中

### Requirement: 开票申请采集中国增值税发票常见信息

开票申请 MUST 采集并保存以下信息：发票类型、抬头类型、发票抬头、纳税人识别号、注册地址、注册电话、开户银行、银行账号、接收发票邮箱、备注。抬头类型为「企业」时，纳税人识别号 MUST 非空；发票类型为「电子专用发票」时，开户银行与银行账号 MUST 非空；抬头类型为「个人」时纳税人识别号 MUST 为空或缺省。接收发票邮箱 MUST 通过邮箱格式校验。

#### Scenario: 企业抬头缺少纳税人识别号
- **WHEN** 用户以「企业」抬头提交申请且未填写纳税人识别号
- **THEN** 系统 MUST 拒绝创建申请

#### Scenario: 专用发票缺少开户行信息
- **WHEN** 用户选择「电子专用发票」但未填写开户银行与银行账号
- **THEN** 系统 MUST 拒绝创建申请

#### Scenario: 个人抬头允许税号为空
- **WHEN** 用户以「个人」抬头提交申请且未填写纳税人识别号
- **THEN** 系统 MUST 接受该申请

#### Scenario: 接收邮箱格式非法
- **WHEN** 用户填写的接收发票邮箱不是合法邮箱格式
- **THEN** 系统 MUST 拒绝创建申请

#### Scenario: 开票信息随申请一并保存
- **WHEN** 一条申请创建成功
- **THEN** 系统 MUST 原样保存用户填写的全部开票信息与所选充值记录的实付金额明细

### Requirement: 开票申请状态机

开票申请状态 MUST 在以下状态之间流转：`PENDING` → `APPROVED` → `ISSUED`；`PENDING` → `REJECTED`；`PENDING` → `CANCELLED`。处于 `APPROVED`、`ISSUED`、`REJECTED`、`CANCELLED` 的申请为终态，MUST NOT 再发生状态流转。对已终止的申请重复执行审核 MUST 返回错误而不是修改状态。

#### Scenario: 待审核申请审核通过
- **WHEN** 管理员审核通过一条 `PENDING` 申请
- **THEN** 申请状态 MUST 变为 `APPROVED`
- **AND** 记录审核人与审核时间

#### Scenario: 已开票申请不可再审核
- **WHEN** 管理员尝试审核一条 `ISSUED` 或 `REJECTED` 的申请
- **THEN** 系统 MUST 拒绝并返回错误
- **AND** 申请状态 MUST 保持不变

#### Scenario: 驳回必须填写原因
- **WHEN** 管理员驳回一条申请但未填写驳回原因
- **THEN** 系统 MUST 拒绝该操作

### Requirement: 用户查看与取消自己的开票申请

系统 SHALL 为用户提供本人开票申请列表与详情，详情 MUST 包含关联的充值记录明细。用户 MUST 只能查看与操作本人的申请。处于 `PENDING` 的申请 MUST 允许用户取消；其他状态 MUST NOT 允许取消。

#### Scenario: 用户取消待审核申请
- **WHEN** 用户取消自己的一条 `PENDING` 申请
- **THEN** 申请状态 MUST 变为 `CANCELLED`

#### Scenario: 取消已审核的申请
- **WHEN** 用户尝试取消一条 `APPROVED` 的申请
- **THEN** 系统 MUST 拒绝该操作

#### Scenario: 无法操作他人申请
- **WHEN** 用户尝试取消或查看其他用户的开票申请
- **THEN** 系统 MUST 拒绝该操作

### Requirement: 管理端查看与筛选开票申请

管理端 SHALL 提供开票申请列表，支持按状态、用户、发票抬头等关键字筛选，并支持分页。列表项 MUST 包含申请 ID、用户信息、抬头、金额合计、状态、申请时间。申请详情 MUST 包含完整的开票信息与关联的充值记录明细。

#### Scenario: 按状态筛选
- **WHEN** 管理员按状态 `PENDING` 筛选
- **THEN** 系统 MUST 只返回待审核的申请

#### Scenario: 按用户筛选
- **WHEN** 管理员按指定用户筛选
- **THEN** 系统 MUST 只返回该用户的申请

#### Scenario: 按关键字搜索抬头
- **WHEN** 管理员按发票抬头关键字搜索
- **THEN** 系统 MUST 返回抬头包含该关键字的申请

#### Scenario: 详情包含充值明细
- **WHEN** 管理员查看一条申请的详情
- **THEN** 响应 MUST 包含该申请占用的每一笔充值记录的订单 ID、订单号、支付时间与实付金额

### Requirement: 管理端登记实际开票信息

管理员 MUST 能在审核通过后登记实际开具的发票信息：发票号码、发票代码、开票金额、开票日期。开票金额 MAY 与申请金额合计不同（以登记值为准）。登记成功后申请状态 MUST 变为 `ISSUED`。

#### Scenario: 登记开票信息
- **WHEN** 管理员为一条 `APPROVED` 的申请登记发票号码与开票金额
- **THEN** 申请状态 MUST 变为 `ISSUED`
- **AND** 系统 MUST 保存发票号码、发票代码、开票金额与开票日期

#### Scenario: 开票金额与申请金额不同
- **WHEN** 管理员登记的开票金额与申请金额合计不同
- **THEN** 系统 MUST 以登记的开票金额为准保存并展示
- **AND** MUST 保留原始的申请金额合计

#### Scenario: 未审核通过不得登记开票
- **WHEN** 管理员尝试为一条 `PENDING` 的申请登记开票信息
- **THEN** 系统 MUST 拒绝该操作

### Requirement: 管理端菜单提供发票申请入口

管理端侧边栏 MUST 提供「发票申请」菜单项，指向开票申请列表页。没有菜单入口的管理端页面无法被管理员访问，等同于功能未交付。

#### Scenario: 管理员从菜单进入开票申请列表
- **WHEN** 管理员在管理端侧边栏点击「发票申请」
- **THEN** 系统 MUST 导航到开票申请列表页并加载申请数据

### Requirement: 用户端页面提供开票申请入口

用户端 MUST 提供开票申请页面，包含可开票充值记录的勾选列表、已选金额合计展示、金额下限提示与申请表单，以及本人申请列表。已选金额合计未达到下限时，前端 MUST 阻止提交并给出提示。

#### Scenario: 未达下限时阻止提交
- **WHEN** 用户勾选的记录合计为 250 元并点击提交
- **THEN** 前端 MUST 阻止提交并提示还需补足多少金额

#### Scenario: 达到下限时允许提交
- **WHEN** 用户勾选的记录合计达到 300 元
- **THEN** 前端 MUST 允许提交申请

### Requirement: 管理端接口纳入管理密钥权限目录

每一个新增的管理端开票接口 MUST 按 HTTP 方法与完整 Gin 路径登记到管理端权限目录中。受限管理密钥 MUST 只获得被显式授予的权限，接口 MUST NOT 继承同目录的其他权限。

#### Scenario: 受限管理密钥访问未授权接口
- **WHEN** 一个未被授予开票权限的管理密钥访问开票申请列表接口
- **THEN** 系统 MUST 拒绝该请求

#### Scenario: 授权后访问开票接口
- **WHEN** 一个被授予开票权限的管理密钥访问开票申请列表接口
- **THEN** 系统 MUST 允许该请求

### Requirement: 开票申请不改变既有充值与支付流程

开票申请 MUST 仅读取充值订单数据，MUST NOT 修改充值订单的金额、状态或支付信息，也 MUST NOT 触发任何支付、退款或余额变动。

#### Scenario: 申请不改变订单状态
- **WHEN** 一笔已支付的充值订单被纳入开票申请
- **THEN** 该订单的金额、状态与支付信息 MUST 保持不变
